# ksctl v0.2.0 Release Design

## Goal

Prepare and publish `v0.2.0` from the current `main` branch. The release must
accurately describe the user-visible changes since `v0.1.0`, point README
installation commands at the new version, pass the repository's full
verification gates, and produce both configured release archives before the
tag is pushed.

## Scope

The release preparation changes only:

- `CHANGELOG.md`, to add the dated `0.2.0` release section and comparison
  links; and
- `README.md`, to update the installation example from `v0.1.0` to `v0.2.0`.

It does not change Go code, dependencies, workflow permissions, supported
platforms, or the GoReleaser archive layout. Version-looking values in command
examples that identify KubeSphere, Kubernetes, or Extension versions remain
unchanged.

## Release Notes

`CHANGELOG.md` retains an empty `Unreleased` section for future work and adds
`[0.2.0] - 2026-07-30` below it. The release notes summarize the complete
user-visible delta since `v0.1.0`, including:

- Extension discovery, lifecycle management, configuration, placement,
  waiting, status, and diagnosis;
- `auth whoami` and best-effort server-side token revocation during logout;
- executable plugin dispatch and plugin diagnostics;
- tenant Workspace, Namespace, and Cluster inspection;
- kubeconfig generation;
- Kubernetes-compatible `logs` and `top`;
- authenticated raw KubeSphere API requests;
- resource-command-local Namespace selection; and
- the release-only `unictl-ks` companion archive.

The changelog adds an `Unreleased` comparison link from `v0.2.0` to `HEAD` and
a `0.2.0` comparison link from `v0.1.0` to `v0.2.0`. Existing `0.1.0` release
notes and links remain intact.

## Verification Gates

No release tag is created unless all of the following pass from a clean
release commit:

1. `make verify VERSION=v0.2.0`, covering formatting, module tidiness and
   verification, vet, normal tests, race tests, and a version-injected `ksctl`
   build.
2. `goreleaser check`, validating the release configuration.
3. `goreleaser release --snapshot --clean`, building the Linux and macOS
   amd64/arm64 archives for both `ksctl` and `unictl-ks` plus
   `checksums.txt`, without publishing.
4. Inspection of the snapshot artifact names, checksum coverage, and the
   version output of both locally built entrypoints with
   `v0.2.0` linker injection.
5. `git diff --check` and a clean worktree after the release commit.

Generated `bin/` and `dist/` artifacts remain untracked and are not committed.

## Commit, Tag, and Publication

The release preparation is committed with a concise release-specific commit
message and pushed to `origin/main`. Before tagging, the local and remote
`main` commit IDs must match and no remote `v0.2.0` tag may exist.

The release uses an annotated `v0.2.0` tag, matching the existing `v0.1.0`
tag style. The tag is created only on the verified release commit and then
pushed explicitly to `origin`. Pushing the tag triggers the existing Release
workflow, which repeats `make verify VERSION=v0.2.0` and publishes the GitHub
Release through GoReleaser.

After the push, the Release workflow is monitored to a terminal state. A
successful release is confirmed by the presence of eight platform archives
(four for each entrypoint) and `checksums.txt`. If local GitHub credentials or
network access prevent the push or workflow inspection, the tag is not moved
or recreated; the exact blocker and the local repository state are reported.
