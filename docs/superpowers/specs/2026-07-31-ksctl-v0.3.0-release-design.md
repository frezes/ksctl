# ksctl v0.3.0 Release Design

## Goal

Prepare and publish `v0.3.0` from the current `main` branch. The release must
describe the complete user-visible and downstream-consumer delta since
`v0.2.0`, update the README installation example, and publish the configured
archives through the existing GitHub Release workflow.

## Scope

Release preparation updates:

- `CHANGELOG.md`, adding the dated `0.3.0` release section and comparison
  links;
- `README.md`, updating the installation example from `v0.2.0` to `v0.3.0`;
  and
- the release design and implementation-plan documents under
  `docs/superpowers/`.

It does not change Go behavior, dependencies, supported platforms, workflow
permissions, or the GoReleaser archive layout.

## Release Notes

`CHANGELOG.md` retains an empty `Unreleased` section and adds
`[0.3.0] - 2026-07-31` below it. The release notes cover the full delta from
`v0.2.0` to the release commit:

- the `kube` command suite, providing kubectl-compatible Kubernetes
  operations through KubeSphere authentication and Cluster routing;
- the breaking move of `describe`, `logs`, and `top` from the root command to
  `kube describe`, `kube logs`, and `kube top`;
- the breaking move of `--request-timeout` from the root command to the
  `kube` command group;
- the breaking Go module path change from `github.com/kubesphere/ksctl` to
  `kubesphere.io/ksctl` for downstream Go consumers;
- fixes for nested `kube` help, visible connection flags, upgraded transport
  configuration, and request-timeout test stability; and
- documentation updates for the revised command and package structure.

The changelog changes the `Unreleased` comparison base from `v0.2.0` to
`v0.3.0` and adds a `0.3.0` comparison link from `v0.2.0` to `v0.3.0`.
Existing release notes and links remain unchanged.

## Pre-Publication Checks

Per maintainer direction, this release does not run local tests,
`make verify`, `goreleaser check`, or a GoReleaser snapshot build.
Pre-publication checks are limited to:

1. reviewing the release documentation diff;
2. confirming the worktree is clean after the release-preparation commit;
3. confirming local `main` and `origin/main` identify the same commit before
   tagging;
4. confirming the remote does not already contain `v0.3.0`; and
5. checking the relevant GitHub credentials and latest `main` CI state.

Generated `bin/` and `dist/` artifacts are not created or committed.

## Commit, Tag, and Publication

The release preparation is committed with a concise release-specific commit
message and pushed directly to `origin/main`.

The release uses an annotated `v0.3.0` tag. The tag is created on the pushed
release commit only after the remote tag-absence and branch-alignment checks,
then pushed explicitly to `origin`. Pushing the tag triggers the existing
Release workflow, which runs `make verify VERSION=v0.3.0` and publishes the
GitHub Release through GoReleaser.

The workflow is monitored to a terminal state. Success requires a published
GitHub Release containing eight platform archives—four each for `ksctl` and
`unictl-ks`—plus `checksums.txt`.

If a pre-publication check fails, no tag is created. If the tag-triggered
workflow fails, the published tag is retained and is not moved or recreated;
the failing workflow and resulting release state are reported exactly.
